# SP4RK

Discord-бот для организации ивентов гильдии. Полностью переписан на модульную архитектуру, с поддержкой нескольких игр и одной командой на весь функционал.

## Что нового по сравнению со старой версией

- Одна команда - `/spark`, доступна только администраторам. Всё остальное (создание ивентов, настройка игр и классов, шаблоны, роли админов) делается кнопками и выпадающими списками, а обычные меню больше не плодят цепочку сообщений - экраны редактируются на месте.
- Бот теперь мультиигровой. У каждой игры свой набор классов, свои шаблоны и свои ивенты. Классы одной игры никак не пересекаются с классами другой.
- У классов теперь настоящие иконки-картинки (с поддержкой прозрачного PNG), а не просто эмодзи-символ. Загружаются через API бота как emoji приложения - видно везде: в списке записи, в кнопках, в карточке ивента.
- Под карточкой ивента можно прикрепить горизонтальный баннер - отдельная рамка с картинкой прямо под основной информацией.
- Автоповышение из запаса: если основной участник отменяет запись, первый подходящий из очереди запасных автоматически занимает его место и получает личное сообщение об этом.
- Кнопка отмены записи теперь сначала уточняет: перезаписаться другим классом или отменить запись совсем. Это защищает от случайной потери места.
- Повторяющиеся ивенты: у шаблона можно включить еженедельный автопостинг.
- Дата и время ивента всегда вводятся и хранятся по московскому времени. Игроки при этом видят время в своём личном часовом поясе автоматически - это делает сам Discord через специальную метку времени, отдельно настраивать ничего не нужно.
- Нативные события Discord (Scheduled Events) синхронизируются с ивентом автоматически.
- Карточка ивента хранится дольше после завершения - сутки, а не час, - и удаляется по времени окончания (старт плюс длительность), а не по времени старта.
- Добавлена простая статистика посещаемости, экспорт состава в файл, дублирование ивента, ручное досрочное закрытие записи, массовое уведомление участников и сохранение опубликованного ивента как шаблона.
- Кнопки "Помощь" и "Мои ивенты" переехали с главного меню на карточку самого ивента - они там нужнее, потому что ими пользуются обычные игроки, а не администраторы.
- Встроенный FAQ прямо в интерфейсе: при первом выборе "запасной" или "возможно" бот присылает короткое пояснение, что это значит.

Старый функционал никуда не делся: лимиты по классам, общий лимит состава, шаблоны, роли администраторов сверх обычных прав Discord, ЛС-напоминания с личным тумблером, архивация после старта, скачивание логов.

## Требования

- Python 3.11 или 3.12. **Не ставь на Python 3.13+** - discord.py всё ещё тянет модуль `audioop`, который Python удалил из стандартной библиотеки начиная с 3.13. На 3.11/3.12 всё работает без танцев с бубном.
- PostgreSQL 16 (поднимается через `docker-compose.yml`).
- Пакеты из `requirements.txt`, включая Pillow - он нужен для подгонки баннеров и иконок классов под нужный размер.

## Запуск

```bash
cp .env.example .env
nano .env

docker compose up -d
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
alembic upgrade head
python main.py
```

## Обновление с прошлой версии бота

Твои старые файлы миграций (`alembic/versions/0001` - `0008`) трогать не нужно, они остаются как есть. В этой сборке добавлены две новые миграции.

`0009_multi_game_schema`:

- заводит таблицы `games` и `game_classes`;
- создаёт под твою текущую гильдию игру **Where Winds Meet** и переносит туда все существующие классы, ивенты и шаблоны без потерь;
- дополнительно создаёт вторую игру - **World of Warcraft: Forever** - пустую, готовую под добавление классов через меню;
- добавляет поля под баннеры, повторяющиеся ивенты, досрочное закрытие записи и синхронизацию с Discord Events;
- заводит таблицу истории посещаемости, которая переживает удаление самого ивента из базы.

`0010_class_icon_emoji`:

- добавляет у классов поля под иконку-картинку (id и имя emoji приложения). Старые классы просто останутся с обычным эмодзи, пока ты не загрузишь им картинку через меню заново.

`0011_class_specs_roles`:

- добавляет у классов необязательную ссылку на родительский класс (`parent_class_id`) и роль (`role`: танк, лекарь, дамагер). Так классы можно превратить в двухуровневую структуру класс - спек (нужно для игр вроде WoW, где под одним классом несколько специализаций); для игр без спеков (вроде Where Winds Meet) ничего менять не нужно, классы работают как раньше. Роль настраивается отдельно в меню "Игры и классы" у каждого класса или спека.

Если у тебя уже есть плоский список спеков World of Warcraft (Afflic Warlock, Arcane Mage и так далее), после `alembic upgrade head` один раз запусти:

```bash
python scripts/migrate_wow_specs.py
```

Скрипт сам создаст базовые классы (Warlock, Mage, Warrior и т.д.), разложит по ним существующие спеки и проставит роли. Ничего не удаляет, спеки не из списка не трогает.

Порядок действий:

```bash
pip install -r requirements.txt
alembic upgrade head
python main.py
```

После апгрейда все твои старые ивенты и классы окажутся внутри игры Where Winds Meet - ничего вручную переносить не надо.

## Тестовый запуск рядом с рабочим ботом

Если у тебя уже крутится старый бот в проде на одном сервере и ты хочешь опробовать эту версию на другом сервере, не трогая старую:

1. Заведи **новое приложение и нового бота** в Discord Developer Portal - именно нового, не переиспользуй токен старого бота. Один процесс на токен, не больше.
2. У нового бота включи Message Content Intent (вкладка Bot, Privileged Gateway Intents) и пригласи его только на тестовый сервер через OAuth2 → URL Generator (scopes: `bot`, `applications.commands`).
3. Подними отдельную базу для теста - либо второй Postgres, либо просто другая база на том же сервере (`spark_db_test` вместо `spark_db`). Смешивать тестовые и боевые данные не нужно.
4. Сделай отдельный `.env` для тестового запуска - с новым `DISCORD_TOKEN` и новым `DATABASE_URL`. Эта версия бота работает в любом количестве серверов одновременно (гильдия определяется автоматически), так что для теста просто запускаешь этот код с тестовыми переменными из отдельной папки/checkout - старый бот в это время продолжает работать как ни в чём не бывало.
5. Раз база новая и пустая - `alembic upgrade head` просто накатит все миграции по порядку с нуля, отдельно переносить нечего.
6. Добавь в тестовый `.env` `SYNC_GUILD_ID=<id тестового сервера>` (правой кнопкой по серверу в Discord с включённым режимом разработчика → Copy Server ID). С этой переменной команда `/spark` появится на тестовом сервере сразу после запуска, без ожидания глобальной синхронизации Discord (та может занимать до часа). На проде эту переменную просто не указывай - там подойдёт обычная глобальная синхронизация.

Когда протестируешь и решишь выкатывать на боевой сервер - убираешь `SYNC_GUILD_ID`, переключаешь `.env` на боевые `DISCORD_TOKEN` и `DATABASE_URL` (тот, где сейчас крутится старый бот) и на боевой базе уже выполняешь апгрейд по инструкции выше, с переносом данных через `0009_multi_game_schema`, `0010_class_icon_emoji` и `0011_class_specs_roles`. Старый процесс бота на этот момент нужно будет остановить, потому что дальше карточки ивентов обслуживает уже новая версия.

## Discord-права, которые нужны боту

- **Message Content Intent** - включи в Discord Developer Portal, вкладка Bot. Без него не заработает загрузка картинок для баннеров и иконок классов (бот ждёт следующее сообщение с вложением в канале).
- **Manage Events** - право на сервере, нужно, чтобы бот мог создавать и обновлять нативные события Discord (Scheduled Events) для каждого ивента. Без этого права ивенты всё равно будут работать, просто без записи в календаре сервера.
- Обычные права на отправку сообщений, вложений и управление сообщениями в тех каналах, где будут появляться карточки ивентов.
- Иконки классов создаются как emoji приложения бота - это действие авторизуется самим токеном бота, отдельных прав на сервере под это не нужно.
- Команда `/spark` по умолчанию видна только тем, у кого есть право "Управлять сервером" (это настройка Discord, её можно донастроить в Integrations на сервере). Внутри бота действует ещё и своя проверка - через роли администраторов SP4RK.

## .env

```env
DISCORD_TOKEN=твой_токен
DATABASE_URL=postgresql+asyncpg://spark_user:spark_password@localhost:5432/spark_db
TIMEZONE=Europe/Moscow
SYNC_COMMANDS=true
DEBUG=false
LOG_FILE=logs/sp4rk_errors.log
GUILD_NAME=Stormchasers

DEFAULT_REMINDER_MINUTES=30
DEFAULT_EVENT_DURATION_MINUTES=180
EPHEMERAL_DELETE_AFTER=60
RAID_PURGE_AFTER_HOURS=24

BANNER_STORAGE_DIR=storage/banners
BANNER_WIDTH=900
BANNER_HEIGHT=260
BANNER_UPLOAD_TIMEOUT_SECONDS=120
BANNER_MAX_UPLOAD_MB=15

BRAND_COLOR=0x5865F2
BOT_STATUS=✨ Записываем на ивенты
```

`TIMEZONE` - часовой пояс, в котором бот понимает дату и время, введённые при создании ивента. По умолчанию Europe/Moscow, и в этой версии он общий для всех админов - персональный часовой пояс на пользователя убран за ненадобностью, потому что игроки и так видят время в своём поясе через метку Discord.

`RAID_PURGE_AFTER_HOURS` - через сколько часов после **окончания** ивента (старт плюс длительность) карточка удаляется из чата и из базы. По умолчанию 24 часа. `EPHEMERAL_DELETE_AFTER` отдельный и относится только к скрытым (эфемерным) уведомлениям бота - подтверждениям и подсказкам, его трогать не обязательно.

`BANNER_STORAGE_DIR` - папка на диске, где хранятся уже обработанные картинки баннеров. Если разворачиваешь бота в Docker, примонтируй эту папку как volume, иначе баннеры пропадут при пересборке контейнера.

## Как устроен баннер

Баннер - это картинка под основной карточкой ивента, в отдельной рамке. Правила:

- Рекомендуемый размер задаётся в `.env` (по умолчанию 900×260). Можно прислать картинку любого размера - бот сам аккуратно обрежет её по центру или растянет под нужные пропорции, без искажений.
- Текста на баннере нет и не будет - это чисто декоративная картинка, вся информация об ивенте остаётся в тексте выше.
- Левый край картинки плавно уходит в прозрачность, по диагонали от угла - визуально баннер как будто растворяется в карточке.
- Если ивент создан **из шаблона**, баннер берётся из шаблона и не спрашивается заново - один раз загрузил при создании шаблона, и дальше он переиспользуется каждый раз.
- Если ивент создаётся **не из шаблона**, бот один раз попросит прислать картинку прямо в чат следующим сообщением. Формат: PNG или JPG, до `BANNER_MAX_UPLOAD_MB` мегабайт.

## Как устроены иконки классов

При создании класса бот спросит картинку следующим сообщением в чате - точно так же, как при загрузке баннера. Картинка автоматически приводится к квадрату (обрезка по центру) и уменьшается до аккуратного размера иконки, прозрачность у PNG сохраняется.

Технически это загружается как **emoji приложения бота** (Application Emoji) - не эмодзи сервера. У этого способа два плюса: во-первых, иконка реально показывается рядом с названием класса везде, включая выпадающие списки при записи (обычную картинку туда вставить нельзя, Discord поддерживает там только эмодзи). Во-вторых, лимит на такие эмодзи не делится с обычными эмодзи сервера - у бота свой собственный лимит, гораздо больше.

Если пропустить загрузку картинки (написать "отмена"), класс создастся с обычным текстовым эмодзи ⚡, как раньше.

## Мультиигровость и структура базы

Вместо отдельной SQL-таблицы под каждую игру используется одна общая схема с полем `game_id` у всех связанных таблиц (`games`, `game_classes`, `raids`, `raid_templates`). Это осознанное решение: заводить новую SQL-таблицу на лету при нажатии кнопки "Добавить игру" было бы рискованно и плохо дружило бы с Alembic-миграциями. С единой схемой данные каждой игры так же легко фильтруются и правятся руками через `WHERE game_id = ...`, но без риска сломать структуру базы.

Логика записи игрока не меняется: у каждого конкретного ивента игра уже зафиксирована (её выбирает админ при создании), поэтому при нажатии "Записаться" игрок сразу видит выбор класса, без лишнего шага выбора игры.

## Логи

Обычный спам APScheduler скрыт при `DEBUG=false`. Ошибки и предупреждения пишутся в файл из `LOG_FILE` и доступны в Discord через меню `/spark` → Логи.
